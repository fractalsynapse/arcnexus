Observed failure: retained 84-37-owner-tests.log, SHA-256 a2843862fce6120eab0a7d9653d13cdc2d4b511d6bb97465fe08725ffd4aff20, shows the real-quality test failing its lint-diagnostic assertion because Bubblewrap could not create a namespace. The test stopped at that assertion, so it did not establish the subsequent type diagnostic. Preserve this infrastructure failure alongside the other failing regressions. The inspected packages/execution/src/check.ts invokes /usr/bin/bwrap with --unshare-all, a disposable worktree overlay, read-only dependencies and common directory, cleared environment and network isolation; it does not contain --disable-userns. Absence of that option does not establish why nesting failed. Bubblewrap documents that protection depends on the supplied arguments and that outer restrictions can affect applications’ own sandboxing. [Bubblewrap 0.11.1](https://github.com/containers/bubblewrap/blob/v0.11.1/README.md).

Smallest proposed design: extend the existing test composition, without changing production execution. mcp-repair.test.ts already connects a real MCP client to LocalMcp, dispatches through ActivationTools, uses a real HostTask journal and checked edits, and substitutes task.check with t.mock.method. Its ordinary case currently manufactures exit 37; its separate native case uses the real confined check. Use the same test-only substitution for a diagnostic composition, but execute the actual declared Foundation command as a child process in an isolated fixture under the already-confined outer test process. Capture actual stdout/stderr, exit or signal, argv, cwd and duration; write each result to a distinct retained artifact and journal its owner/activity/expectation. Do not intercept /usr/bin/bwrap, replace the production process launcher, add an operation handler, or fall back from a failed native attempt. The explicitly controlled boundary is HostTask.check: its production inner sandbox and cache are outside this test’s proof. Children inherit the outer sandbox; that is not proof that the omitted inner sandbox would enforce its own policy.

Use an isolated copy with the locked toolchain available and a captured owner that has lintable TypeScript but no suites, as quality-real-failures.test.ts already discovers using Foundation’s selectQualityInputs and hasOwnerTestSuites. Resolve discovery in the fixture’s directory, preferably in a separate child process so process-wide cwd is not changed during concurrent tests. Preserve the actual catalog and tool configuration. Obtain file selections and identities from Foundation rather than duplicating its globs, ignores or ownership logic. Establish baseline diagnostics, introduce a method-length defect and a number/string assignment defect only in disposable fixture content, and require the actual lint rule diagnostic and TS2322 for the selected file. A nonzero exit alone is insufficient: namespace, missing-tool and configuration errors do not demonstrate lint/type behavior.

The commands to execute in that proposed fixture are npm run lint -- <owner>, npm run check, and npm run format:check -- <owner> when formatting is an obligation. package.json maps lint and format:check to the Foundation owner-quality runner; check is tsc --noEmit and remains repository-scoped. Do not invent an owner argument for the existing type command or broaden owner lint/format to repository scope. owner-quality.ts calls selectQualityInputs, prints selection and content identities, and invokes the configured real tool. Dependency preparation is a prerequisite, not a synthetic successful check. These are proposed commands; this research activation executed none of them and changed no files.

Same-caller sequence: from one connected MCP client, invoke each captured check with expected=pass; assert the response contains its actual failing status and retained diagnostic log. Repair the disposable fixture through the existing checked-edit operation with its current digest, preserving earlier successful receipts. Invoke the checks again from the same caller and require fresh passing results while the first failed logs remain unchanged. Configure the fixture activity with the required operation bindings. Use the existing steward and Workflow composition demonstrated in steward-check.test.ts to assert that an empty completed response, omitted operation, unrelated pass or unrelated inapplicability cannot advance the milestone. Count activation/Direction/delivery calls: ordinary correction must stay in the original milestone, and delivery must remain behind the existing assembled acceptance boundary. A controlled delivery service proves orchestration only; it does not prove a real GitHub merge. ActivationTools.finish alone is not the progression gate.

E-1: keep ownership-drift, collision, unknown-owner and Foundation selection-parity tests independent of the diagnostic substitution. The current check.ts only implements owner-test-suites inapplicability, so the owner format/lint applicability gap remains a real implementation issue. The substituted check must not be used to claim that production captured ownership or applicability is correct. Record operation, owner, activity, selected scope, identity and precise operation-specific inapplicability; an empty suite set says nothing about lint/type applicability.
