# Research report

## Decision

Design meaningful Workflow public-boundary refinement regressions using the existing real Execution, Coordination SQLite and Git lifecycle without fabricating completed-round events.

## Findings

Research question: Identify the existing public test fixtures and exact setup for an admitted foreground parent and sequential Planner, Architect and standing-goal children, including explicit no-change provider responses, retained SQLite/Git state, observer events and a controllable child-terminal/parent-acknowledgement interruption. Decision: Design meaningful Workflow public-boundary refinement regressions using existing real Execution, Coordination SQLite and Git lifecycle without fabricating completed-round events.

1. Available fixtures and their limits

packages/execution/tests/fixtures/architecture.ts exports ArchitectureFixture. It creates a real committed Git repository, separate application storage, Coordination, and actual parent/child HostTask instances. Its parent uses Coordination.admit; its child uses parent.journal.child. decide(answer?) obtains a real host decision receipt through HostTask.requestDecision. GitHub transport is isolated while Git checkpoints remain real. This is useful for exact approvals and declines, but it pre-admits a delivery child and constructs Capture directly: it is not a full Execution.admit fixture for sequential refinement phases.

packages/execution/tests/fixtures/checkpoint.ts exports RecoveryScenario with public root, storage, services, remote, run(), advance(), observe(), abandonWorkspace(), and identity/worktree observations. It exercises Workflow, real SQLite, Git worktrees, checked edits and checkpoint recovery, including a push accepted remotely before its response is lost. Its admission constructs HostTask directly, and its final verification/delivery ports are controlled fixtures. Reuse its recovery patterns and existing regressions; do not describe it as real preflight admission or proof of hosted integration.

apps/cli/tests/fixtures/project.ts exports projectFixture(): string. It commits a generic catalog, roles, profile, operations, guidance and contract registry. It lacks delivery/check configuration, executable bindings, Planner/Architect bindings and standing goals required for this scenario. It is a starting point for a complete temporary target, not a ready refinement fixture.

packages/execution/tests/fixtures/provider-events.ts is an executable fixture, not a factory. It emits thread start, an unknown Unicode-bearing event, a complete tool result, usage and a structured final answer. packages/execution/tests/integration/native-events.test.ts demonstrates copying the compiled fixture to an executable with the current Node shebang, binding it in HostConfig, invoking HostTask.activate and reading actual native observation artifacts. Its final answer is {kind:'completed'}, so refinement requires explicit phase-specific responses. The local NativeScenario, PlannerRepairScenario, AssessmentFixture, SessionFixture and RefinementFixture classes are not exported reusable fixtures.

2. Exact public-service composition

Create a temporary parent directory containing sibling project and state directories. Commit the complete generic project catalog and source to real Git. Configure a canonical HTTPS GitHub origin, a staging branch distinct from protected main, nonempty project.checks.acceptance, and declared Planner, Architect, Director and Reviewer activities with explicit fixture profiles. Write .git/bindings.yaml with schemaVersion: 1 and tools.codex set to an absolute executable fixture path. Keep the checkout clean and storage outside the project. These requirements come from packages/execution/src/host-config.ts; an empty executable or partial Capture from the smaller fixtures cannot exercise Execution.admit.

For deterministic staging observation without GitHub network dependence, a test-owned local bare Git remote with an HTTPS-to-local Git transport mapping is a possible setup; this is a recommendation, not an existing fixture found in the consulted files. Ensure the captured and configured origin identity remains the canonical HTTPS value. Exercise actual Git commits and staging movement rather than mocking the selected revision.

Construct Architecture, Coordination(storage), Execution(architecture, coordination, storage), Agent and Planner through their public entries. Compose WorkflowServices using closures that call the real Execution methods, preserving their this binding. Use planner.propose/apply and Architecture.propose through their normal ports. Keep ordinary Direction, agent, Verification and Delivery paths for engineering scenarios; substitute only explicit provider/external transport boundaries. Construct new Workflow(services).

Execution.admit(input, signal, parent?: TaskSession) is the public child admission seam. It resolves fresh staging for every child, verifies that the parent journal belongs to the same project database, then calls Journal.child. Workflow.run(input, observer, signal, parent?) and Workflow.update(directory, feedback, observer, signal, parent?) already forward parent sessions. Planner children use TaskInput.planning = 'exploration'; standing-goal children use standing: true and the exact captured goal.body. Give every phase and goal a stable invocation/round-specific scope. Workflow.update currently hardcodes architecture:update; repeated Architect phases therefore still need a round-specific identity handoff.

At each phase transition, attempt Coordination.admit for a competing root and assert refusal naming the foreground root. Journal.child.close does not close the shared connection, and child.finish cannot release the parent. An active child blocks siblings and ancestor finish. These behaviors already have real SQLite regressions in child-sessions.test.ts.

3. Explicit valid no-change responses

Planner's provider response is a Proposal, not {kind:'planned'}. Supply summary, ratings, comparison, changes: [], links: [], and sources. For exploration, ratings must contain each captured goal exactly once. A practical rating uses alignment:'strong', evidence:'unverified', a meaningful reason, an exact captured source citation and observations:[]; do not claim demonstrated evidence without a valid verified-run citation. The empty-ratings fixture in planner/tests/integration/response-repair.test.ts applies only to an empty inventory. Real Planner.propose validates the response, stores goal-mapping.md, journals plannerProposal, and returns a planned TaskOutcome.

Architect's explicit provider response is {kind:'no-change', summary:'The declared requirement is aligned.', evidence:[{path:'contract.md', quote:'| SERVICE-1 | Original requirement |'}]}. The cited bytes must exist in the admitted capture. architecture-assessment.test.ts demonstrates both successful validation and repair of an empty citation list.

Director's response is {kind:'satisfied', summary:<meaningful assessment>, evidence:[{path:<captured file>, quote:<exact excerpt>}]} for an initial standing-goal assessment. Pass the real StandingGoalEvidence from Execution.observeGoal. Do not bypass a runtime-dependent success measure: observeGoal identifies measures requiring run evidence. Use source-verifiable requirements for the minimal no-change scenario, and retain separate real check/publication scenarios for measured execution. Every captured goal must still invoke Direction on every fresh round.

4. Retained state and interruption control

Keep the same repository, storage, canonical remote, exact goal text and scopes across attempts. Finish/close sessions through the normal Workflow lifecycle; remove fixture directories only after the entire retry scenario. Reconstruct services for the second invocation so the test demonstrates persisted recovery rather than an in-memory cursor. HostTask.observations reads retained and current events; HostTask.history exposes Workflow checkpoints; journal.taskID identifies the logical session while journal.run identifies an attempt.

Coordination already exposes admit(remote, goal, fresh, scope, cycle), Journal.childEvents(goal, scope), round(remote, captureInventory, namespace), and completeRound. Its cycle admission preserves unfinished identity and allocates a fresh identity after a refined terminal outcome. childEvents reads complete retained child history under the parent's logical identity. completedTask is narrower: it recognizes merged/satisfied outcomes and a supplied task scope, so it is not a substitute for reading Planner/Architect child history.

A precise interruption seam already exists: HostTask.finish first commits Journal.finish, then synchronously invokes the TaskObserver.event listener. In a Workflow-owned subprocess scenario, watch JournalEvent.parent and observation.outcome to identify the selected successful child; terminate the fixture process from that callback before it returns. The child's terminal transaction has committed, but Workflow has not returned the child result to its parent. Retry from a new process against the same SQLite/Git state. Assert the actual successful child outcome is reused, the provider/delivery call count does not increase, and the parent records recovery. This requires no invented completion event or production crash hook.

For a lighter deterministic variant, throw a unique fixture interruption from the committed child-terminal observer. Workflow.complete closes the child in finally; the parent lifecycle can record failure. This exercises the acknowledgement gap but is not evidence of abrupt writer death. Merely aborting the signal in that callback may allow synchronous parent acknowledgement and is therefore insufficient to guarantee the gap.

packages/coordination/tests/fixtures/crashed-writer.ts and child-sessions.test.ts establish real SIGKILL/departed-writer recovery, but their current fixture kills an unfinished nested child. Extend the scenario pattern to a real Workflow-produced successful terminal callback; do not copy the manually authored outcome records from the Coordination storage tests as refinement evidence.

5. Observers, reports and prior-finding consumption

Use TaskObserver.progress, event, measurements and answer. JournalEvent contains sequence, run, taskID, goalID, optional parent, timestamp, observation and optional live detail. HostTask.listen creates a registered run-timeline.jsonl artifact. HostTask.note persists an index and can forward complete transient detail; originating payloads remain in registered immutable artifacts. run-timeline.test.ts verifies this distinction.

RunObserver.for reuses one projection across sequential children. Use real controlled provider activation to generate nativeStarted/nativeEvent/nativeFinished records and provider usage, then reconcile observed measurement snapshots against those records. The provider-events fixture supplies input_tokens:100, cached_input_tokens:80, output_tokens:20 and reasoning_output_tokens:5, plus an unknown event and complete tool data. Do not manufacture usage by directly recording events in the refinement acceptance scenario. Mocking HostTask.activate is suitable for response-validation tests but bypasses the native stream needed for measurement assertions.

The documented target is CompletedRefinementRound exported by Workflow and used in TaskEvent as {completedRound: CompletedRefinementRound}, carrying invocation, round, report, findings, measurements and evidence. packages/workflow/refinement.md explicitly says this is a forthcoming public handoff, not an available fixture. After implementation, complete round one through Workflow.refine; observe its actual completion event and registered report; then assert that prepared Planner, Architect and Director requests in round two expose and consume distinct originating findings and measurement references. Repeat across a fresh invocation. Preserve complete findings/answers and unknown usage/pricing values. Never seed a completedRound record to make this test pass.

6. Missing seams and accountable owners

Workflow currently has no refine method, refined TaskOutcome or CompletedRefinementRound type. Its refinement.test.ts only asserts the absent boundary for pre-admission cancellation. Workflow owns the sequencing, durable total/cursor, round-specific phase identities, aggregate outcome and actual completed-round production.

Execution.round(directory) and goalRound currently do not expose Coordination's namespace parameter. WorkflowServices.execution.round has the same limitation. The Execution supplier should expose the minimal namespace handoff while Workflow supplies invocation/round identity; standalone inventory must retain its independent namespace. Execution.admit currently enables cyclic root admission only for input.architecture. TaskInput has no refinement/cycle discriminator, so a normal refinement root also needs an explicit admission handoff rather than pretending to be an architecture command.

TaskSession exposes typed record/history, but no child-history or registered-report-storage methods. Native HostTask publicly exposes journal.childEvents, observations, store and readFile. Workflow can use the existing native public boundary where appropriate; if Workflow must remain independent of HostTask, add the smallest service-port exposure for those operations. No additional database or interruption-hook framework is needed.

The prior-round consumer path is also missing: activation.ts currently adds the task timeline and retained task evidence; plannerAssignment supplies inventory and verifiedRun; Journal.findings selects failures/repairs, not completed refinement rounds. Execution owns carrying Workflow's eventual public completed-round observation into actual actor context. The end-to-end supplier test cannot honestly pass until both the producer and this consumer handoff exist.

7. Regression allocation

Place the new real-boundary scenarios under Workflow-owned integration tests, using public package entries and a Workflow-owned generic fixture rather than importing another owner's private scenario classes. Cover two complete rounds with multiple goals, passing-measure Direction calls, competing roots between phases, exact-total retry/refusal, interruptions in every phase and goal, pending/approve/skip gates through TaskObserver.answer, immutable captured Run inventory, fresh next-round inventory, fresh completed invocations and committed-child recovery. Preserve real checkpoint/publication regressions for unchanged machinery. Keep CLI parsing, JSONL terminal uniqueness and cancellation tests in the CLI/Commands boundary; task-jsonl.test.ts supplies the existing terminal-adapter pattern. A no-change refinement round proves orchestration and observation, not steward delivery or live acceptance.

## Unresolved

- Workflow must settle the minimal public service shape for refinement root admission, round-specific Architect scope, child-history recovery and report storage; current TaskInput/TaskSession/WorkflowServices do not expose the complete handoff.
- Execution must expose namespaced inventory selection and consume actual Workflow-produced completed-round findings in later Planner, Architect and Director requests.
- No consulted exported fixture combines complete Execution preflight, real staging transport, all three explicit assessment providers and successful-child crash timing. A Workflow-owned fixture must compose these existing boundaries.
- The proposed local bare-remote transport mapping and successful-terminal subprocess interruption need implementation and observed regression evidence; they are concrete test designs, not already executed fixtures.
- Mandatory assembled verification, independent assessment, staging delivery and the separate live qualification remain outside this research assignment.
