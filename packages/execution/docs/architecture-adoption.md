# Approved architecture during an active task

Execution uses its existing workspace setup and activity checkpoint boundaries to
apply and adopt an Architect delivery. It does not replace an in-flight Agent
request or introduce another scheduler. The exact proposal and its original
baseline must have a genuine host approval from the admitted Architecture parent.
Model checked edits cannot invoke this capability.

The host applies exact reviewed bytes through the existing single-file checkpoint
path. It captures the resulting real Git commit through Architecture, validates
Team coverage, selected request bindings, local handlers, required check mappings
and command availability, and revalidates retained checked owners and pending
activities. Candidate guidance outside the reviewed batch is refused. An unavailable
handler or command retains its diagnostic and the previous authority while normal
prerequisite work can continue. Final assembly requires successful adoption.
Availability validation does not replace behavioral tests, independent verification
or staging checks; a command's availability does not prove its implementation correct.

The journal records an `architectureAdoption` before switching the active capture,
with the exact approval receipt, old/new revisions and running Node entrypoint.
Restart reconstructs that same committed architecture after recovering the worktree.
It revalidates the candidate rather than treating a recorded transition as new
permission. Completed observations keep their recorded architecture version.

The admitted `config.capture` remains the original engineering and approval
baseline. The active `capture` is the architecture used by the next request,
operation resolver, Team lookup and check-input identity. Candidate diffs and
publication retain the original engineering base, so adopting architecture cannot
hide the guide changes or make the task appear unchanged. Accepted milestones and
criteria are retained in the existing Workflow journal; adoption does not reconstruct
the Director plan. Caller inbox identities remain tied to their admitted context,
preserving complete answered questions and acknowledged edit receipts.

This path does not load a new runtime automatically. The recorded entrypoint
identifies the runtime actually executing. A future runtime update still requires
its validated safe boundary. Missing code or handlers cannot be made usable by
approving declarations alone.

When staging advances between attempts, recovery uses the admitted current
architecture to validate retained checked owners and pending activities. It merges
the secured checkpoint with staging through Git's ordinary three-way merge.
Independent changes within one file are compatible; textual conflicts retain the
checkpoint and exact merge diagnostic. A whole-file architecture or guidance
change is not itself a conflict. A changed owner or unavailable pending activity
still prevents resumption, and changed candidate inputs require fresh verification.
Exact protected proposals keep their original baseline and require reconciliation
and renewed approval when that baseline changes.
