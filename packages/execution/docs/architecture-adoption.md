# Approved architecture during an active task

Execution uses its existing workspace setup and activity checkpoint boundaries to
apply and adopt an Architect delivery. It does not replace an in-flight Agent
request or introduce another scheduler. The exact proposal and its original
baseline must have a genuine host approval from the admitted Architecture parent.
Model checked edits cannot invoke this capability.

The host applies exact reviewed bytes through the existing single-file checkpoint
path. It captures the resulting real Git commit through Architecture, validates
Team coverage, selected request bindings, local handlers, required check mappings
and command availability, and revalidates retained checked owners and pending
activities. Candidate guidance outside the reviewed batch is refused. An unavailable
handler or command retains its diagnostic and the previous authority while normal
prerequisite work can continue. Final assembly requires successful adoption.
Availability validation does not replace behavioral tests, independent verification
or staging checks; a command's availability does not prove its implementation correct.

The journal records an `architectureAdoption` before switching the active capture,
with the exact approval receipt, old/new revisions and running Node entrypoint.
Restart reconstructs that same committed architecture after recovering the worktree.
It revalidates the candidate rather than treating a recorded transition as new
permission. Completed observations keep their recorded architecture version.

The admitted `config.capture` remains the original engineering and approval
baseline. The active `capture` is the architecture used by the next request,
operation resolver, Team lookup and check-input identity. Candidate diffs and
publication retain the original engineering base, so adopting architecture cannot
hide the guide changes or make the task appear unchanged. Accepted milestones and
criteria are retained in the existing Workflow journal; adoption does not reconstruct
the Director plan. Caller inbox identities remain tied to their admitted context,
preserving complete answered questions and acknowledged edit receipts.

This path does not load a new runtime automatically. The recorded entrypoint
identifies the runtime actually executing. A future runtime update still requires
its validated safe boundary. Missing code or handlers cannot be made usable by
approving declarations alone.

When staging advances between attempts, recovery uses the admitted current
architecture to validate retained checked owners and pending activities. It merges
the secured checkpoint with staging through Git's ordinary three-way merge.
Independent changes within one file are compatible; textual conflicts retain the
checkpoint and exact merge diagnostic. A whole-file architecture or guidance
change is not itself a conflict. A changed owner or unavailable pending activity
still prevents resumption, and changed candidate inputs require fresh verification.
Exact protected proposals keep their original baseline and require reconciliation
and renewed approval when that baseline changes.

## Required verification before Architect completion

The accepted intent for `ownership-audit-completion` closes the Architect
completion gap under Execution's required-verification obligation and EX-27,
together with Architecture's operation-binding obligations and ARC-25. It needs
no contract amendment. The approved batch's baseline is
`6822549788fc58643b7277fe8315a20c406b828a`; its prerequisite
`ownership-audit-cli` supplies the candidate command through Commands and
Architecture's public service. This section guides the Execution implementer and
reviewer; enforcement and native evidence remain to be established.

Architecture updating must satisfy every required applicable check declared by
its captured activity before either a proposal or a justified no-change response
can finish assessment. If the model omits invocation, the host runs the declared
verification. A direct MCP invocation and automatic completion use the same
captured binding, typed defaults and overrides, host identity and resolved argv.
A model cannot change a required passing check to expected-red. Inapplicability
must come from the existing declared mechanism; a missing executable, setup
failure or disabled native scenario cannot supply passing evidence.

Extract reusable completion verification from the ordinary steward path in
[steward.ts](../src/steward.ts), retaining its pending-check reconciliation and
required-operation behavior. Reuse [ActivationTools](../src/activation-tools.ts),
the [shared command resolution and confinement](../src/check.ts), and existing
evidence applicability handling. Generic Execution must select the captured
activity's verification bindings without naming this repository's ownership
command or copying the steward verification loop. The operation declaration
remains the source of executable and argument configuration; the activity
references that same binding as a tool and completion requirement.

A failed audit or unavailable executable returns the actual operation identity,
status or availability diagnostic and complete retained log to the accountable
Architect caller before assessment can finish. Preserve earlier successful
receipts, complete answers and failed observations. Question, research and
supplier handoffs keep their existing sequential continuation; they are not
completion claims. Verification neither approves a proposal nor applies protected
bytes. Changed proposal bytes, intent or baseline retain the exact human approval
rules described above. Local corrections follow
[Workflow's repair boundary](../../workflow/contract.md).

Reuse an observation only when the existing applicability identity establishes
unchanged relevant candidate inputs, captured authority, resolved operation
parameters and environment. Changes to working-tree catalog data or audited Git
inventory must prevent reuse of a stale ownership result. Keep the original
observation and obtain fresh applicable evidence through the existing check path;
do not create a second evidence cache.

Before recording adoption, validate executable and runtime availability for the
actual next activation and confined check environment. A declaration, a handler
name or installation in an unrelated Host image is insufficient. Identify the
candidate-built entry point and runtime that provide the approved operation.
Availability validation and behavioral evidence serve different obligations.
Preserve the original engineering base and acceptance, and retain the actual
authority identities of historical activations through any validated transition.

The distinguishing regression is an Architect returning a valid proposal or
no-change response without calling a required check: completion must invoke that
check and refuse progression when it fails. Extend the existing
[activity-verification scenarios](../tests/integration/activity-verification.test.ts)
and [Architecture assessment scenarios](../tests/integration/architecture-assessment.test.ts)
to cover both response forms, omitted invocation, failed and successful audits,
unavailable executables, changed inputs and identical direct/automatic resolution.
Retain ordinary steward coverage and handoff behavior. Controlled-provider
observations establish response handling; combined-candidate evidence must also
run the candidate-built command against real Git inputs through the actual
confinement boundary and retain command, argv, cwd, runtime identity, exit and log.
Applicable owner checks and the host's assembled verification remain required.
Independent acceptance and staging publication belong to the existing
[Delivery service](../../delivery/contract.md).
