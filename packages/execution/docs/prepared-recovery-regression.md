# Prepared recovery regression design

The Testing contribution for `prepared-recovery-continuity` extends the existing
[checkpoint scenarios](../tests/integration/checkpoint.test.ts) with
[prepared recovery scenarios](../tests/integration/prepared-recovery.test.ts).
It implements the [recorded recovery intent](prepared-checkpoint-recovery.md)
without changing product behavior, contracts or acceptance.

## Boundary and discriminating assertions

The caller is Workflow over production Execution admission, preparation and
assembly, real Architecture capture, Agent request construction and HostTask
activation. A committed generic temporary project supplies ownership, roles,
profiles, operation mappings, registry and an explicit executable provider.
The provider invokes production LocalMcp to secure one checked file and request
a human answer. Workflow's actual foreground answer handler supplies a distinct
multiline value with leading whitespace, Unicode, trailing spaces and a final
newline. The fixture interrupts before activity completion is acknowledged,
reopens Coordination's SQLite state and advances staging through real Git.

For `recovery-history-preserved`, assertions compare the exact recorded answer
and canonical answer artifact before interruption, the resumed provider's actual
assignment, the retained receipt, original base and original accepted criterion.
The issue and task identities remain identical. The preserved receipt must be
the only acknowledged edit receipt; the question must be prompted once.
An unchanged-staging control receives the exact answer after restart.
These assertions reject answer paraphrasing, dropped caller input,
current-attempt-only history, repeated prompts and duplicate acknowledged edits.

For `recovery-current-capture`, the resumed session must contain the new staging
revision, exact current owner roots and both original and newly applicable
acceptance check IDs. The actual provider tool discovery must expose the new
read operation together with the original edit and question operations.
Its request retains the original milestone criterion and identifies the new
revision and configured model/executable. Separate committed captures move the
checked file to another owner or remove the pending activity. Each must refuse
before another provider activation or checkpoint movement. This rejects stale
capture continuation and synthetic ownership that never reaches the public path.

For `recovery-conflict-retained`, overlapping additions must retain the original
branch head, remote checkpoint and exact checked contribution. The diagnostic
must contain Git's complete merge-tree output, including stage entries and
messages, rather than just a generic conflict status. Compatible changes retain
both contributions and original checked blob identity. Another staging advance
requires another captured base and Git reconciliation. An explicitly reconstructed
abandoned clean workspace represents the retained crash window; recovery must
inspect and remove it before creating a distinct workspace. This characterizes
restart handling, not an actual operating-system process crash.

## Observed red and retained evidence

At the Testing source baseline, the new recovered-answer assertion fails:
`assignment.clarifications` is undefined after staging moves, although the
original exact answer and checked receipt remain in retained observations.
The unchanged-staging control and changed-owner, unavailable-activity, complete
conflict, repeated-staging and abandoned-workspace scenarios pass.
The intended failure is lost answer delivery across a changed capture, not
provider setup, a missing executable or a TypeScript failure.

The retained mapped owner-tests observation is
`125-474-owner-tests.log` in this task's host evidence directory. It records the
actual command and behavioral failure. Each native source artifact is copied
once, with its original path, SHA-256 and complete text, into that enclosing
check log before temporary fixture cleanup. These diagnostics are never fed
back into subsequent provider requests. The request, invocation, transcript,
stderr, MCP results and clarification artifacts remain auditable there.
Earlier invalid-plan and missing foreground-answer fixture observations are
retained as setup feedback and do not establish the intended red.

## Scope of the evidence

This is deterministic executable-provider evidence through real Git, SQLite,
request construction and local MCP. Direction planning, final Verification and
Delivery use explicit controlled collaborators; a fixture `merged` result
does not establish a real independent verdict or GitHub merge.
The new captured acceptance check selection is asserted, not executed by those
controlled final gates. No claim is made about live model compliance, native
check confinement, hosted CI, uncertain PR reconciliation or final delivery.
Those remain with the later accepted milestones and host assembled verification.
The existing skipped native cases remain gaps, not passes.

At the original Testing position this public regression was deliberately left
red for Implementation to restore caller answer continuity without reauthorizing
an old host approval. Exact proposal, candidate and verification gates retain
their current identities; original acceptance and observations remain history.

The [implementation record](prepared-recovery-implementation.md) retains the
subsequent run 125 pass. The [run 145 characterization](prepared-checkpoint-recovery.md#executed-prepared-recovery-characterization-run-145)
records current passing execution of these unchanged sources, caller-consumer
recovery and authority identity coverage, with exact evidence references and
quality observations. No new behavioral red or product correction was needed.
The controlled final gates still do not establish independent acceptance or
hosted publication recovery.
