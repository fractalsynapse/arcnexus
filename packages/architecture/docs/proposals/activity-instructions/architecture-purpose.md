# Architecture component purpose

## Turn human direction into one coherent operating model

Architecture maintains the human-guided model that tells ArcNexus what its Agents
are for, how components compose and which operations each activity may use. Its
product service resolves that model, validates its relationships and assembles the
single complete request used by inspection and activation. Its component steward
maintains the catalog, interface records and architectural explanations under the
architect's authority. These responsibilities belong together because a declaration,
its resolved meaning and the context an actor receives must agree.

The architecture is an integrated data structure rather than a collection of
unrelated prompt fragments. Project identity and bindings, components, roles,
profiles, operations, standards, ownership, verification and contract authority
refer to each other. An activity with excellent prose but an unavailable operation
cannot complete its work. A valid operation attached to the wrong profile can
pass a superficial file check and fail at activation. Architecture must expose
those relationships early and deterministically, with a diagnostic that identifies
the actual source of the inconsistency.

Agent and Team are the conceptual center of this model. An Agent combines a
component's purpose and selected activity with its observations and capabilities.
Team exposes the eligible members and canonical ownership decisions. Architecture
supplies the approved definitions those services use. It should be possible to
inspect one actor, understand its complete operating procedure and follow its
relationships to the rest of the team without reconstructing several competing
catalogs or reading every activity in the repository.

The word model has two meanings in this system and must remain clear. The
architectural model is the resolved project data described here. A provider model
is the language model selected by an execution profile. Architecture resolves the
profile and preserves its identity, but the two concepts are not interchangeable.
An architectural update can change instructions or operation bindings without
changing the provider. Token measurements do not authorize a cheaper profile,
and a provider's capacity does not justify adding an arbitrary architectural cap.

## Public responsibilities and consumers

Capture resolves a project from a directory and committed source revision. It
verifies the declared canonical repository identity, reads the registry and
accepted definitions, validates locked content and returns a stable source for
resolution. A caller should be able to name the actual revision and reproduce
its definitions. Capture must not silently contact an upstream service, consult
an unrelated working tree or interpret a convenient local file as approved
authority. Credentials and executable host composition have their own trusted
boundaries.

Request preparation resolves a component and explicit activity, including special
Director and Reviewer selectors, then assembles the complete selected context.
Agent inspection, Commands and actual activation consume that same builder.
The existing request remains one input string with source-attributed sections and
separate invocation options. The purpose and activity text form the actor's
operating instructions; task values and observations retain their own provenance
within that string. No second private provider prompt should replace what a
human inspected.

Validation checks meaningful relationships as well as syntactic shape. Component
identity must match its definition, required activity references must resolve,
ownership must be complete and unambiguous, locked digests must match and mapped
operation categories must be compatible with their profiles. Explicit empty
collections remain empty. Host-only activities retain their own executor and no
model profile. A missing mapping is a finding to report, rather than a reason
to inherit an activity or silently drop an unavailable capability.

Architecture assessment evaluates accepted objectives and goals, current guides,
implementation and relevant prior observations. It returns a justified no-change
assessment or a reviewable exact proposal with purpose, consequences and any
required implementation. Workflow places that assessment inside the Architect
phase, and Commands provides a transport-neutral gateway. The Architecture Agent
can investigate and ask optional research questions; it cannot approve itself or
write protected source through an ordinary model edit.

Execution consumes resolved operations, ownership and guidance when activating an
actor or validating an approved model transition. Verification consumes the
candidate's applicable authority and checks. Foundation supplies shared tooling
and low-level utilities, while its specification entry and Architecture validation
must agree about declared relationships. Direction and Planner read the same
accepted structure for different decisions. Architecture should make those
consumers consistent through public services rather than by copying internal
parsers into every plugin.

## Resolve explicit definitions without inventing authority

Project-level defaults may supply missing non-activity properties only where the
accepted property permits inheritance. Ownership and authority remain explicit.
Each component authors its own activity map, and the mapping selects its role,
profile, instructions, operations and standards. A missing activity is unavailable.
An empty list contributes nothing. These rules keep a human's omission or explicit
restriction meaningful instead of allowing a generic default to create capability.

Permitted objects merge recursively through one rule. Explicit scalars and arrays
replace defaults, including false values and empty arrays. Concatenating operation
lists or treating an empty list as absent can silently broaden grants. Preserve
the provenance of effective values so inspection and diagnostics can explain
where a default or override came from. Avoid a new expression language, implicit
policy engine or project-specific merge exception when simple declared data can
represent the intended configuration.

Roles provide standing guidance and responsibilities; they own no files or
commands. Profiles select provider settings and permitted operation categories.
Operations declare actual handler or executable behavior. Standards reference
complete authored material selected for the activity. Components define ownership
and purpose. Keep each fact at its source and reuse it by reference. An activity's
long instructions can explain how to use a capability without redefining its
command, schema or permission in conflicting prose.

Complete definitions remain readable from the captured source. The active request
includes the acting component's full purpose and selected activity procedure, with
relevant role and standards. Other components appear in a compact index with
identity, source reference and any explicitly authored short summary. This avoids
duplicating every expanded purpose while preserving discovery. Do not manufacture
a summary by cutting off a purpose, omit needed selected text or impose a content
ceiling to make assembly easier.

Source-backed instruction documents can make substantial procedures maintainable
when the approved representation supports them. Their selection must be explicit,
their content complete and their provenance preserved. They remain architectural
guidance, covered by the same proposal and adoption boundary as inline text.
There is no reason to add recursive templating, excerpt selectors or another
prompt store for ordinary file composition. The architect reviews the complete
result, and the runtime continues using one request builder.

## Reusable operations and immediate verification

Operation definitions describe the executable act and its parameters, prerequisites,
working directory, network policy, confinement and model-facing schema where
applicable. A declaration must correspond to an available implemented handler or
command before activation. Approving a name is not installing its behavior.
Architecture validation should identify an unavailable binding before an Agent
spends an activity trying to invoke it. The resulting refusal must preserve the
source and precise field that needs correction.

Typed parameters let components reuse an operation for different test strategies
and other legitimate configuration. Resolve declared defaults, explicit component
values and activity binding overrides in order. Keep authoritative host identity
values distinct from permitted invocation parameters. A test selector can choose
declared tags, level or paths only when the underlying command supports that API.
The same resolved values must appear in inspection, execution and evidence identity.

Interpolate parameter values into executable arguments as data. A scalar remains
an argument, while an array expands to argument entries. Literal metacharacters
must not become shell syntax. Unknown parameters, invalid types and attempts to
rewrite executable identity or expand confinement are findings, not opportunities
for permissive coercion. Keeping this resolver canonical prevents a check from
meaning one thing in a preview and another when the host executes it.

Activity verification references its resolved operation bindings rather than
copying their configuration. Testing can retain an identified expected-red
observation separately from required passing format, lint, types and build.
Implementation obtains applicable current passing checks. An owner without a
behavioral suite remains valid, and suite absence does not waive the other
operations. The host's assembled checks remain independent requirements. Prose
and declarations should make those distinctions clear before self-review finds
an avoidable deterministic failure.

Check reuse depends on actual effective inputs and environment. A changed
parameter, source, authority or dependency can invalidate the affected observation.
Unknown coverage calls for a fresh conservative check rather than a speculative
dependency-analysis framework. Architecture supplies the resolved identity and
declared applicability; Execution records the actual observation. Foundation
provides reusable selection and tool behavior. Avoid turning architecture
assessment into a continuous owner-by-owner dependency approval service.

## Architectural change is a reviewable guide decision

The Architecture Agent studies the accepted direction and actual implementation
together with prior execution findings. It should identify a concrete useful gap,
explain its consequences and propose the smallest coherent correction. A justified
no-change result is valuable when existing guides fit. Repeated execution is
not a reason to invent architectural edits, and a noisy log is not automatically
evidence that another layer or plugin is required. Prefer fixing the responsible
existing declaration or simplifying an unnecessary mechanism.

An exact proposal names its baseline, intent, consequences, prerequisite
implementation and complete proposed file contents. The host derives any required
registry changes from the contract changes and includes those exact bytes before
asking for approval. Stages and prior history remain consistent. A model-supplied
digest or an edited candidate registry cannot make a contract accepted. The human
must be able to review the actual change, not a vague promise that the host will
fill in important details later.

Human approval binds the exact proposal and baseline. Absent or unknown approval
preserves a pending decision. Decline leaves accepted authority intact. Changed
intent or bytes require renewed review, and a moved baseline requires explicit
reconciliation rather than silently rebasing protected edits. Preserve the
verbatim decision and all earlier failed observations in the existing journal.
Implementation repair within accepted intent can continue without creating an
additional human gate for routine engineering.

Ordinary checked editing refuses protected source even when the Architecture
steward owns its directory. Ownership and authority are different conditions.
The steward can prepare a proposal in its ordinary owned documents, but the
trusted host applies exact approved bytes through its narrowly scoped capability.
That capability validates the proposal, approval, original digests and intended
result together. It is not a model tool or a general privileged file writer.
The separation prevents an architecture-editing Agent from approving its own rules.

Architecture must keep the human's guides separate from generated plans and
learning. Planner owns durable objectives and owner-free goals. Direction generates
the task sequence. Reviewer derives evidence-linked lessons. Those records can
inform an architectural assessment without becoming immediate authority. A useful
lesson becomes a durable standard only through the architect's accepted guide
change. A goal remains an aspiration and measure, not a storage location for
passing check logs or current component assignments.

## Deliver prerequisites inside Architect

Some proposals need implementation before their declarations can work. An operation
may need a real handler, an override may need command support or a new context
source may need a resolver. The proposal identifies those outcomes, and Workflow
uses the normal Director/steward task lifecycle inside the Architect phase.
Contributions retain their accountable owners, checked edits, applicable checks,
independent verification and staging delivery. Architecture does not create a
second engineering loop to bypass those responsibilities.

Prerequisite sequencing must be concrete. Implement the lower-level public seam
before a dependent consumer needs it, and reserve the full collaboration proof
for assembled integration. A valid intended-red test need not wait for its future
implementation to pass. Missing operations should be corrected at their actual
owner instead of forcing repeated Foundation investigations. A request for another
owner supplies real required work or an answer; agreement-only conversations add
cost without making a declaration usable.

Approved protected bytes and their required implementation form one coherent
candidate. Availability and acceptance remain different. The host can validate
that a handler exists and safely adopt an exactly approved model at an activity
boundary, while the combined candidate still needs independent assessment and
staging delivery. A passing declaration check cannot stand in for a real native
observation, and an accepted design cannot turn simulated output into delivered
provider behavior.

After accepted prerequisite delivery, the following Run phase captures the
accepted architecture for its work. It must not continue against an obsolete
catalog merely because an earlier phase started with it. At the same time, a
task's original acceptance and historical evidence retain their identities.
Architecture supplies the resolved new model; Workflow owns phase progression,
Execution owns actual session enforcement and Coordination retains the transition.
These services share one lifecycle and store.

## Evolve safely during a run

Architecture is actively evolving under human guidance. The host reloads the
integrated model at new admission and after an applied approved update at a safe
activity boundary. Finish or cancel an in-flight activation before changing what
the next one receives. Context, Team, operation parameters, MCP grants and
verification must advance together. A partly updated model can be worse than an
explicit hold because it makes the actor reason under contradictory capabilities.

Revalidate pending work and retained checkpoints against the new authority.
Preserve original acceptance, complete answers, successful edit receipts and
failed observations. Compare actual ownership and affected operation identity,
then refresh evidence whose relevant inputs changed. Retain unaffected observations
when they still apply. An incompatible transition should produce a precise
architectural finding instead of dropping work, widening permissions or silently
continuing against an unsupported operation.

Runtime adoption needs its own trusted validation and actual identity record.
Candidate source cannot replace the host composition merely because its catalog
declares a new plugin or provider. A validated updated runtime can be adopted at
a safe boundary through the approved lifecycle; keeping an old supervisor frozen
forever is not the objective. Architecture must describe the trusted composition
and its available services without introducing an alternate runtime manager or
uncontrolled plugin installation path.

Restart preserves the transition's causality. The old proposal baseline identifies
what was approved, the engineering base defines the contribution, the active model
governs the next actor and the candidate identifies what was assessed. Do not
collapse those meanings into one mutable revision field. A recovered approved
change must recognize its acknowledged protected writes, retain its exact receipt
and avoid duplicate publication. Tests should exercise real committed sources
and the existing journal rather than constructing unrelated strings that merely
look like those identities.

## Evidence and characteristic failure modes

A declaration can be syntactically valid while its activity is unusable. A profile
category mismatch, missing standard source, unknown handler or unavailable command
must be caught through the same resolved meaning used by activation. Offline
validation and inspect should agree. Fix the canonical responsible validation
path and keep the diagnostic's component, activity, operation and profile context.
Do not broaden the profile or skip the binding just to make validation pass.

Prompt drift is another boundary failure. A request can include all component
activities instead of the selected one, duplicate foreign purposes or lose source
labels during serialization. Long content must remain complete, and explicit
empty task values must not be replaced by invented placeholders. Verify the
rendered and structured inspect forms and actual adapter input for identical
inputs. A substring assertion that passes because a serializer wrapped text does
not prove full preservation or proper selection.

Approval drift is especially dangerous. A proposal may have changed after review,
a registry may omit prior history or a current candidate may claim a human receipt
from another baseline. Test absent, declined, forged, changed and stale decisions
through the public proposal/application boundary. Keep negative observations
readable. Correctly refusing an invalid approval is a successful boundary check;
it is not a reason to weaken the guard to keep a live task moving.

Instruction quality also belongs to this component's stewardship. A sentence that
names an activity without teaching its decisions leaves agents to rediscover
operations, fixture shapes and recovery routes. Author detailed component-specific
procedures, reuse shared protocols once and inspect the complete resolved prompt.
Use observed mistakes as concrete cases, including a test waiting for its own
future implementation, a wrong-owner write after a successful edit and an answer
lost during nested repair. Length supports useful detail but never proves quality
by itself.

## Measures and continuous learning

For example, a component may need the same test operation to select different
declared tags in Testing and Implementation. The operation definition supplies
the parameter type and default; each explicit binding supplies its permitted
override. Inspection should show those different argv values, Execution should
run them literally and reuse must distinguish them. A source fixture with an
empty override should preserve that empty collection. These observations prove
the reusable architectural mechanism without adding separate command implementations
or a hardcoded rule for today's component names.

Consider an approved update that adds a quality operation before its real command
exists. Approval establishes human intent but not executable availability. The
Architect phase must deliver the required command support and exact guide change
through their owners, then validate the combined result. The next activity can
use the operation only after the recorded adoption boundary. A refusal that
identifies the missing executable is useful feedback; silently substituting a
different check would conceal the gap and invalidate the acceptance claim.

Consider instead a long purpose document changed in an ordinary candidate edit.
Its useful prose does not make it approved instruction authority. The active
capture and request remain unchanged, the protected source boundary refuses an
unauthorized write and a legitimate revision follows the exact proposal route.
After approved application, a fresh request must include the complete new text
with its source, while the previous activation's retained request still contains
the actual older text. This is observable guided evolution, preserving both
adaptability and evidence honesty without freezing the whole project.

Architectural tests should make each of those distinctions visible at the public
boundary. A fake capture with a missing field can hide the very behavior being
claimed; a realistic committed fixture supplies the actual registry and source
relationships. Keep deterministic resolution evidence distinct from real confined
operation evidence and live self-development. The final refinement report links
them instead of treating any one category as a universal substitute.
Every report distinguishes proposed guidance, applied authority and demonstrated
behavior, so an approved design is never presented as a working implementation.

Success means the accepted catalog resolves coherently, invalid relationships fail
before activation, inspection matches execution and exact approved updates reach
the next legitimate activity without losing work. A person can identify where
each purpose, instruction, operation value and acceptance obligation came from.
The Architect phase can deliver useful approved guide refinement together with
working prerequisites and supply that accepted model to subsequent work.

Measure the time and profile usage spent reaching those outcomes. Repeated
assessments that reconstruct the same obsolete proposal, copy bulky history or
send local technical failures back through Direction reveal opportunities for
simplification. Preserve complete reports and diagnostics while keeping the
assessment focused on relevant findings and readable references. Missing usage
and unverified monetary cost remain unknown. Measurement does not authorize
budgets, automatic profile changes or content limits.

Later assessments should consume previous round findings and evaluate whether
an accepted change improved real behavior. Compare useful delivery, local repair,
fixture validity, redundant checks, request sizes and elapsed effort. Record
lessons as observations and propose durable guide changes only when warranted.
The desired architecture is a simple extensible foundation that helps the team
complete its work, with each addition justified by a demonstrated responsibility
and each superseded mechanism removed when the direct path replaces it.
