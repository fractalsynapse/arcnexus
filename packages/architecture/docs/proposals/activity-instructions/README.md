# Detailed operating instructions for every Agent activity

Status: proposed work for efficiency-checklist D, tracked in
[issue #672](https://github.com/fractalsynapse/arcnexus/issues/672) under
[the implementation checklist](../../../../../docs/plans/efficiency-foundation.md).
These drafts are not active instructions or approved architecture. Do not load
them as authority for the retained run or report the catalog rewrite complete.

## Deliverable

Each component needs a substantive purpose and each explicitly declared model
activity needs a complete operating procedure. The requested authoring targets
are 4K tokens for a resolved component purpose and 6K for resolved activity
instructions. Measure the authored sources and the assembled text separately with
an identified tokenizer. Targets guide writing; they are not runtime rejection
rules, quotas or reasons to repeat prose. A longer file is useful only when it
improves a real decision.

The operating procedure must explain the actor's mission, inputs, available
operations, method, meaningful verification, expected response, ordinary repair,
questions, delegation and escalation. Its examples must fit that component's
public contract and actual tool schemas. The Director, Planner, Architect and
independent Reviewer have different decisions from a steward's own documentation,
testing, implementation and self-review. They cannot share an interchangeable
generic prompt. The host-only release activity remains a host specification,
without a model profile or pretend system prompt.

## One authored source and explicit composition

Keep component-specific guidance beside that component's catalog declaration, in
its own directory under `.arc/architecture/components/`. Keep reusable operating
protocols in the architectural guidance space and reference their complete text
explicitly from each applicable activity. This preserves the existing Architecture
ownership of the catalog and its protected-edit boundary; it does not move plugin
implementation, tests or ordinary documentation into another component.

An activity's explicit ordered instruction list can combine a shared Agent
protocol, its activity-specific protocol and a component/activity-specific
document. These are complete source files, not excerpt selectors, templates with
an expression language, paging APIs or implicit inherited activities. A missing
file is a validation error. A supplied empty list stays empty. Neither a role
name nor an automatically expanded generic role completes a component's rewrite.
Review the component-specific text and the complete resolved procedure together.

Inline authored text remains useful for small target projects and explicit test
fixtures. Source references are an alternative representation of authored text,
not a compatibility lifecycle or second prompt builder. Both resolve from the
same captured Git source and preserve exact bytes and provenance. Reference only
architecture-owned guidance in this batch, so current proposal, adoption and
checked-edit protection continue to cover every instruction source. Do not invent
another authority store or allow candidate files to become instructions.

## Separate operating instructions from observations

The shared request builder must expose the complete approved operating instructions
separately from the changing task input. The provider places those instructions in
its supported developer-instruction channel; it receives the goal, assignment,
acceptance, answers, findings and evidence as task data. Role and activity guidance
cannot be demoted to an incidental heading in a user message. Conversely, a log or
research report cannot promote itself into standing policy.

Inspection must display both complete channels with distinct source labels and
the same placeholders and invocation options as activation. Structured inspection
must contain exactly the request the adapter consumes. Actual subprocess evidence
must verify both channels, the selected profile, mapped tools and working directory
for the Director, a steward and the independent Reviewer. Keep Codex's normal
AGENTS.md and skill discovery. Do not replace its base instructions or add a
parallel SDK/provider lifecycle merely to obtain a new field.

This requires an exact amendment to the current CLI request parity wording before
changing locked bytes: GW-26 currently equates the entire rendered prompt with
`request.input`. Architecture and Execution must describe the same new channels,
and the registry must retain stages and prior history. Prepare that complete diff
through the existing proposal/registry builder. Approval of this work record does
not approve unseen contract bytes.

## Decisions drawn from real failures

Testing must establish a relevant assertion at a public boundary, with explicit
fixture authority and actual record shapes. A missing method can be a legitimate
initial red for a new service; a broken fixture, wrong response discriminator,
missing dependency, unintended skip or TypeScript error is not that behavioral
observation. Repair the fixture locally and preserve both observations. Construct
small realistic fixtures rather than importing another owner's private test code.

Sequence contributions by their true dependencies. A lower-level admission or
inventory interface must not wait for its higher-level consumer's finished
implementation just to establish its own contract. Use an explicit contract-shaped
fixture for the lower-level seam and reserve the actual producer/consumer proof
for assembled integration. Where another owner really must supply an interface or
implementation, request that concrete contribution and have Direction place it
before the dependent work. Do not request agreement or create circular fixture
dependencies. This is a central finding from retained run 101's Execution/Workflow
handoff, not a reason to bypass real SQLite/Git verification.

Ordinary check, tool and ownership failures return to their caller. Preserve the
full original finding alongside the current diagnostic; inspect successful edit
receipts before attempting another write. Distinct progress can justify another
correction. Unchanged repetition calls for diagnosis or an explicit escalation,
not a numerical retry budget or an assertion that the requested work is impossible.
Self-review chooses the earliest activity that can change the result. Only an
explicit cross-owner/scope escalation or final independent rejection engages
Direction. Scope and acceptance remain host-controlled.

Research is optional and should settle a named uncertainty. Read relevant existing
reports first, ask a detailed question, and resume with the full answer. Do not
force research before every activity or confuse reading local implementation with
a requirement to perform external research. Complete reports remain reusable
component knowledge, without content ceilings.

The live timeline must inform the actor's choices. It identifies current work,
completed contributions, exact failures, acknowledged effects, pending requests
and measured effort. Retain complete source artifacts and follow their references;
do not copy the entire history into every reply. Reuse check evidence only when
its inputs, parameters, authority and environment still match. Distinguish expected
red, a passing operation, independent acceptance, CI and staging delivery.

## Construction and acceptance

Author and review purposes, common protocols and every component/activity document
against the existing catalog. Preserve profiles, ownership and explicit operation
grants unless an exact approved guide amendment changes them. Audit operations and
verification together with prose, including formatting support for editing and
real native/provider checks where declared. A paragraph grants no tool.

Before changing request behavior, establish focused deterministic failures for
complete source expansion, missing/unsafe references, explicit empty lists,
selection isolation, approved-source protection, channel parity and actual adapter
arguments/stdin. Reuse the unique actual-subprocess fixtures retained in draft
[PR #601](https://github.com/fractalsynapse/arcnexus/pull/601), updating them to the
current contracts and TypeScript standard rather than discarding their coverage.

Validate the complete catalog, all references and bindings, the built inspect
entry, strict types, formatting, lint, ownership, guidance and applicable tests.
Record authored and resolved token counts and actual request sizes without
introducing a size gate. Compare relevant pre-rewrite findings and post-rewrite
decisions when live acceptance is authorized. Static validity and a lengthy prompt
do not demonstrate that an agent performs better.

The architect has prohibited another live test until D is addressed. The retained
run 101 may finish; no new live acceptance is started as part of authoring this
proposal or running deterministic checks. Keep qualification at 0/3 until the full
approved production refinement acceptance actually succeeds.
