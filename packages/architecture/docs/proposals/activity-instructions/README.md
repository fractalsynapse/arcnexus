## Deliverable

Each component needs a substantive purpose and each explicitly declared model
activity needs a complete operating procedure. The requested authoring targets
are 4K tokens for a resolved component purpose and 6K for resolved activity
instructions. Measure the authored sources and the assembled text separately with
an identified tokenizer. Targets guide writing; they are not runtime rejection
rules, quotas or reasons to repeat prose. A longer file is useful only when it
improves a real decision.

The operating procedure must explain the actor's mission, inputs, available
operations, method, meaningful verification, expected response, ordinary repair,
questions, delegation and escalation. Its examples must fit that component's
public contract and actual tool schemas. The Director, Planner, Architect and
independent Reviewer have different decisions from a steward's own documentation,
testing, implementation and self-review. They cannot share an interchangeable
generic prompt. The host-only release activity remains a host specification,
without a model profile or pretend system prompt.

## Actual specifications and one authored source

Rewritten purposes and component-specific activity instructions are authored
**directly in the component YAML specifications**, not in a separate set of
replacement purpose documents. The proposed specifications are in
[the component directory](../../../../../.arc/architecture/components/).
The corresponding role definitions and explicitly selected standards supply
shared procedure through the existing request builder.

The shared [Agent operating protocol](../../../../../.arc/architecture/standards/agent-operating-protocol.md)
is authored once and selected explicitly in each model activity's standards.
Activity-specific shared methods belong in the selected role's instructions;
component-specific method, fixtures, decisions and outputs belong in that
component activity's own instruction paragraphs. The complete activity operating
prompt combines these sources in the existing single request string. Report
both source-specific and complete resolved token counts. Neither a generic role
expansion nor a newly added standard alone completes a component's individual
activity rewrite.

This uses the existing purpose, instructions, role and standard fields. No new
source-reference syntax, loader, templating framework or provider channel is
needed. Each rule has one authored home; complete selected guidance remains
readable with its ordinary source labels. Existing activities, profiles,
ownership and operation authority remain explicit. The host-only release
specification does not acquire a model profile or a generic Agent prompt.

This branch is a review proposal. It is not staging or an adopted runtime model.
Finish every component purpose and activity, then stop for human review before
activation or further live testing. The retained run used its original installed

## Decisions drawn from real failures

Testing must establish a relevant assertion at a public boundary, with explicit
fixture authority and actual record shapes. A missing method can be a legitimate
initial red for a new service; a broken fixture, wrong response discriminator,
missing dependency, unintended skip or TypeScript error is not that behavioral
observation. Repair the fixture locally and preserve both observations. Construct
small realistic fixtures rather than importing another owner's private test code.

Sequence contributions by their true dependencies. A lower-level admission or
inventory interface must not wait for its higher-level consumer's finished
implementation just to establish its own contract. Use an explicit contract-shaped
fixture for the lower-level seam and reserve the actual producer/consumer proof
for assembled integration. Where another owner really must supply an interface or
implementation, request that concrete contribution and have Direction place it
before the dependent work. Do not request agreement or create circular fixture
dependencies. This is a central finding from retained run 101's Execution/Workflow
handoff, not a reason to bypass real SQLite/Git verification.

Ordinary check, tool and ownership failures return to their caller. Preserve the
full original finding alongside the current diagnostic; inspect successful edit
receipts before attempting another write. Distinct progress can justify another
correction. Unchanged repetition calls for diagnosis or an explicit escalation,
not a numerical retry budget or an assertion that the requested work is impossible.
Self-review chooses the earliest activity that can change the result. Only an
explicit cross-owner/scope escalation or final independent rejection engages
Direction. Scope and acceptance remain host-controlled.

Research is optional and should settle a named uncertainty. Read relevant existing
reports first, ask a detailed question, and resume with the full answer. Do not
force research before every activity or confuse reading local implementation with
a requirement to perform external research. Complete reports remain reusable
component knowledge, without content ceilings.

The live timeline must inform the actor's choices. It identifies current work,
completed contributions, exact failures, acknowledged effects, pending requests
and measured effort. Retain complete source artifacts and follow their references;
do not copy the entire history into every reply. Reuse check evidence only when
its inputs, parameters, authority and environment still match. Distinguish expected
red, a passing operation, independent acceptance, CI and staging delivery.

against the existing catalog. Preserve profiles, ownership and explicit operation
grants unless an exact approved guide amendment changes them. Audit operations and
